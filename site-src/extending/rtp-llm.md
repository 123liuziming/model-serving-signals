# RTP-LLM

The RTP-LLM adapter reads JSON from the **Python frontend's `/worker_status`** endpoint.
It does not require a Prometheus endpoint, a KMonitor gateway, or changes to RTP-LLM.
The scraper converts task snapshots into gauge metric families; the existing translator then
maps them using [`catalog/profiles/rtp-llm.yaml`](../catalog/profiles/rtp-llm.yaml).

```sh
go run ./cmd/exporter \
  --profile catalog/profiles/rtp-llm.yaml \
  --engine-scraper rtp-llm-worker-status \
  --engine-host localhost \
  --engine-metrics-port 8000 \
  --engine-metrics-path /worker_status
curl -s localhost:9464/metrics
```

Replace `8000` with the frontend's actual HTTP port. Do not target the C++ HTTP health
endpoint of the same name: it returns cache/health information without task snapshots.
The default `--engine-scraper prometheus` remains unchanged for other engines.

## Supported signals

| Contract signal | Adapter metric | Source |
| --- | --- | --- |
| `gen_ai.server.request.queued` | `rtp_llm_worker_status_requests_queued` | Local tasks in `TASK_PHASE_RECEIVED` or `TASK_PHASE_KV_ALLOCATED`. |
| `gen_ai.server.request.running` | `rtp_llm_worker_status_requests_running` | Local tasks in `TASK_PHASE_RUNNING`. |

The names above are generated by the adapter, not KMonitor metric names. Each DP worker
produces its own series with `dp_rank` and `role_type` labels, including explicit zeros when
its task list is empty. Select one frontend for a worker group to avoid scraping the same
DP workers through multiple frontends. Prefill/decode roles describe local engine work,
not unique end-to-end requests across a disaggregated deployment.

The frontend repeats the first worker at the top level for compatibility. The adapter reads
only `results`, avoiding double counting. Within each result, `running_task_info` contains
both waiting and running tasks, so its length alone is not a running-request count.
`TASK_PHASE_PENDING` represents a record without a local stream (including cancellation
control records) and is excluded. Finished tasks are also excluded. The legacy
`waiting_query_len` and `running_query_len` fields are not populated by the inspected
server implementation and must not be used as counts.

The adapter rejects dead workers, duplicate/invalid DP ranks, missing task data, unknown
phases/roles, and incomplete DP responses. For completeness it uses each backend's
`dp_size`, not the top-level value, which the frontend rewrites to the number of successful
responses. Failed scrapes produce no contract metrics and are logged; they do not produce
zero load. Requests use the exporter's `--scrape-timeout` (default 5 seconds).

## Compatibility and evidence

The response schema and task-state semantics were checked against RTP-LLM commit
[`1812ac310f95d2377d243b5dfa95aff01dc4f065`](https://github.com/alibaba/rtp-llm/tree/1812ac310f95d2377d243b5dfa95aff01dc4f065):

- [Frontend JSON conversion](https://github.com/alibaba/rtp-llm/blob/1812ac310f95d2377d243b5dfa95aff01dc4f065/rtp_llm/utils/grpc_client_wrapper.py#L121): per-DP `results`, protobuf field names, enum names, and string-encoded int64 ranks.
- [Worker status RPC](https://github.com/alibaba/rtp-llm/blob/1812ac310f95d2377d243b5dfa95aff01dc4f065/rtp_llm/cpp/model_rpc/LocalRpcServer.cc#L659): fills task phases, DP metadata, role, and liveness.
- [Runtime task metadata](https://github.com/alibaba/rtp-llm/blob/1812ac310f95d2377d243b5dfa95aff01dc4f065/rtp_llm/cpp/model_rpc/RpcServerRuntimeMeta.h#L31): derives phases from stream state and adds cancellation control records.

This adapter requires that schema, including explicit phase names and per-worker `dp_size`,
`dp_rank`, and `role_type`. It does not infer state from older `is_waiting`-only responses.
Unit tests use source-shaped JSON fixtures. The adapter was also validated against a
live engine built from that commit on 2026-10-22, using CUDA 13.2, an NVIDIA A10, and
Qwen3-0.6B. Three concurrent requests each returned 128 output tokens successfully;
31 exporter scrapes observed queued and running counts reaching 2, and the running
count returned to zero after the requests completed. This was a single-DP,
non-disaggregated deployment; multi-DP and prefill/decode deployments were not
exercised in that run.

## Signals left unmapped

RTP-LLM already has `rtp_llm_wait_stream_size` and `rtp_llm_running_stream_size` KMonitor
instrumentation, but those are a different collection path. The inspected initialization
leaves the Prometheus sink disabled, so a native-name YAML profile alone cannot scrape them.

The request duration and first-token metrics (`rtp_llm_latency_us` and
`rtp_llm_first_token_latency_us`) are KMonitor gauges in microseconds, not the contract's
histograms in seconds. Request duration, TTFT, and per-request mean TPOT are therefore left
unmapped. Polling task snapshots or scaling an aggregated latency gauge cannot reconstruct
those histograms. They require individual request observations, either through engine
histogram instrumentation or a separate trace aggregation path.

### Trace aggregation experiment

The same live engine exported OTLP/HTTP protobuf traces with
`RTP_LLM_TRACE_CONFIG` enabled and `sampler_ratio` set to `1.0`. Ten controlled
`/v1/chat/completions` requests succeeded, and each matched exactly one frontend
SERVER span named `POST /v1/chat/completions` with resource `rtp_llm.role=frontend`.
An offline aggregation of those spans produced:

| Observation | Source | Observations from 10 requests |
| --- | --- | --- |
| Request span duration | End timestamp minus start timestamp, converted from nanoseconds to seconds | 10 |
| Frontend TTFT | `gen_ai.response.time_to_first_token`, converted from milliseconds to seconds | 9 |
| Frontend mean TPOT | `rtp_llm.frontend.time_per_output_token_ms`, converted from milliseconds to seconds | 8 |

The workload contained eight streaming requests with 32 output tokens, one streaming
request with one output token, and one non-streaming request with 32 output tokens.
The non-streaming request omitted both frontend token timing attributes. The
single-token request omitted TPOT. Missing observations must not be replaced with
zeros. Engine CLIENT spans have different timing boundaries and must not be counted
again as frontend request observations.

This demonstrates that request-level timing observations are available; the current
exporter does **not** receive traces or expose these latency histograms. A production
trace aggregation path would need explicit handling of sampling, export loss, retries,
and the streaming-only coverage of frontend token timings. The observed span duration
also includes frontend completion/cleanup work, so its endpoint needs to be assessed
against the contract's last-byte or last-token boundary.
